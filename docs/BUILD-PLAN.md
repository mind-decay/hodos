A stage is done when its report shows every criterion PASS with evidence and the fresh review is ACCEPT (or the user accepted at the breaker).

## Working agreement

- Read `CLAUDE.md`, `docs/README.md`, `STAGE-PROTOCOL.md`, then this stage's entry and every specification section it names, completely.
- Write English. Follow `AUTHORING.md` for every skill, reference, agent, rule, adapter. Run `node scripts/lint.mjs` before reporting (from Stage 0 on, where the v0 lint exists).
- Scope is the stage. Anything discovered outside it goes into `docs/BACKLOG.md` as one line with evidence — not into the code.
- A design change (a new field, cap, phase, file, or threshold) is a decision, not a build step: write the proposal into `docs/DECISIONS.md` under *Proposed*, ask the user with options and a recommendation, and wait.
- Report with evidence: commands run and their output, files created with line counts, lint output. "Done" without output is not done.
- Test with `claude --plugin-dir .` against `bench/fixtures/` — never against a real project before Stage 12.
- Scripts: `node:test` unit tests next to each script, **written test-first** — the failing run before the implementation, and the mutation check after it, are part of the stage report (decision 0022); `npm test` runs them; no dependencies. Node 20 LTS is the pinned CI version (`engines.node: ">=18"`, CI uses 20).
- Commits: conventional, imperative, "why" in the body, no trailers.
- **Interactive evidence.** Headless runs (`claude -p … --plugin-dir .`, check D) serve the bench. Acceptance criteria that need an interactive session (`/plugin`, `/context`, `AskUserQuestion`, killing and resuming a session, transcript review) are run by the **user**: the builder writes `docs/stages/NN-manual.md` — numbered steps, each with the exact command, the fixture copy to use (`bench/scripts/fixture-copy.mjs`), and what to paste back — and the user runs them in a second terminal started with `claude --plugin-dir <repo>` inside the fixture copy, pasting the excerpts. The builder records them in the report as evidence with the label `manual`. Asking the user to run a manual step is not a decision; it is part of every stage from 0 on.

## Stage order rationale

Scripts before skills (skills call scripts); fixtures before kernels (nothing is tested on a real project); S1 before S2 (S2 needs an approved plan); review before verify (verify runs on reviewed code); campaigns after the single-task loop is proven; full init last among features because its rule-quality mechanisms depend on the defaults list and the reviewer that confirm rules; 10b after 10 because it edits what `init` writes and must land before 0.1 publishes the config format; the pilot only after the bench exists, so pilot findings are attributable; 11c before the release because the two commands it adds are public surface and an extension point added after 0.1 is a breaking change to what projects install (decision **0081**, the argument decision 0040 made for the rule form); 9b after the release and before the pilot, because its grammar is provable on a seeded fixture pair while the two things a fixture only imitates — a foreign owner who is a person, a race resolved socially — are what the pilot is for (decision **0077**). 11d after 11b and before 9b, because its changes to `verify.md` are additive and its config fields are written only by the finish it ships — no dormant key reaches 0.1 (decision **0090**) — while the one thing `init` declares, decision **0095**'s two kinds, went ahead into 11b-4; and before the pilot, because a pilot that measures a verify known to skip Q2 and Q4 would have to be re-bought (decisions **0092**–**0099**).
