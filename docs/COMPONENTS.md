# hodos — Component Specifications

One entry per component. Each entry is the contract the builder implements and the reviewer checks against. File shapes are in `FORMATS.md`; writing rules in `AUTHORING.md`; rationale in `DESIGN.md`.

Every entry has: **Purpose · Invocation · Inputs · Outputs · Procedure · Completion · Anti-pattern · Limits · Depends on**.

Shorthand: `ledger.mjs add …` means `node ${CLAUDE_PLUGIN_ROOT}/scripts/ledger.mjs add …`. Scripts are always invoked by that absolute form; the bare name is documentation shorthand only.

## 1. Skills

Every kernel opens with `` !`node ${CLAUDE_PLUGIN_ROOT}/scripts/state-digest.mjs` `` so the project state is present before the first reasoning step, and carries `allowed-tools: Bash(node ${CLAUDE_PLUGIN_ROOT}/scripts/*)` (`PLATFORM-NOTES.md` check J covers the expansion of that pattern). A kernel that needs another skill's procedure invokes that skill through the Skill tool, which is why its target is model-invocable (`PLATFORM-NOTES.md` check H, decision 0016). Reproducing another skill's procedure inline is forbidden: it duplicates the invocation contract at the call site and drifts from it.

### 1.1 `task` — S1 kernel

**Purpose.** Own session 1: route the request, research if needed, grill and plan, obtain approval, hand off to S2.
**Invocation.** `/hodos:task <description>` · `/hodos:task <campaign>/<node>` to start a campaign node.
**Inputs.** The description; `config.json`; campaign maps in scope; existing task dirs.
**Outputs.** `tasks/<slug>/{brief,research,plan}.md`, `ledger.md`, `state.json` (phase `approved`), and the task pointers `.claude/hodos/sessions/<session-id>` and `active`, both written by `ledger.mjs init` (decision 0047); the printed handoff line.

**Procedure (standing).**
1. `config.mjs find`; `notFound` → say "run `/hodos:init` first" and stop (hard dependency).
2. Read `references/route.md`; fill the nine-row checklist with evidence; derive the verdict by the rules in `FORMATS.md §3`; `AskUserQuestion` with the proposed path/type/campaign and the alternatives. On a verdict of `quick`, `standard` or `deep`: derive the slug; `ledger.mjs init <slug> --path <p> --type <t> [--campaign <c/n>]`; write `brief.md`. A campaign verdict opens no task — `ledger.mjs` records a path out of `quick|standard|deep` and a campaign has no path of its own (`FORMATS.md §3`, decision 0031) — so this step is skipped and the printed, confirmed verdict is what step 3 hands over.
3. Campaign verdict → invoke the `campaign` skill through the Skill tool (decision 0016); stop when it returns. Invoked as `<campaign>/<node>` this step is skipped — a node is already scoped, and skipping it is what terminates the `task` → `campaign` → `task` re-entry.
4. Type `question` → answer with sources in chat; `ledger.mjs add "Finish: report delivered"`; stop. No plan.
4b. Type `bug` and no candidate from step 2 is a command that fails as the repository stands: read `references/reproduce.md` and take one of its two exits before any plan exists. Exit A writes a `## Reproduction` block into `brief.md` whose command is T1 of the plan; exit B writes one `Ruling: not reproducible here — …` and **no plan**, because `DESIGN.md §4.1` forbids a `bug` plan with no red loop.
5. Path `deep`, or grilling hits a fact: read `references/research.md`, dispatch Explore subagents (`model: config.models.research`), write `research.md`, run `verify-citations.mjs`.
6. Read `references/plan.md` and `references/design.md`. Grill in rounds until the frontier is empty; every design field filled; decisions table complete; tasks are tracer bullets with acceptance criteria.
7. Path `deep`: dispatch `hodos-plan-reviewer` (`model: config.models.planReview`); fold its findings; at most one repeat.
8. Present the plan summary (goal, decisions, tasks); ask for approval. On approval: create the branch per `config.conventions.branch` (ask if it exists); `ledger.mjs add "Plan: approved" --tasks <n> --branch <name>` (the script records `base` from `git rev-parse HEAD`, sets phase `approved`); print exactly `/clear` then `/hodos:run <slug>`.

**Invariants (first 40 lines of the kernel).** No code is written in S1. References are read on entering their phase, fail-closed. The router spends ≤5 evidence calls (decision 0029). Facts are fetched by subagents, decisions are asked of the human — the grilling agent never answers its own questions. Nothing is assumed silently: every open question has an answer or an owner before approval.
**Completion.** `state.phase == approved` and the handoff line printed.
**Anti-pattern.** Starting to implement "since the plan is small"; a router that opens files to decide; a plan approved with open questions.
**Limits.** Kernel ≤150 lines; references per `AUTHORING.md §7`.
**Depends on.** `config.mjs`, `ledger.mjs`, `verify-citations.mjs`, `campaign`, `hodos-plan-reviewer`.

#### `references/route.md`
Procedure: extract intent; classify type (`feature/bug/refactor/question/spike/upgrade`, the last two by the tests of `FORMATS.md §3`); fill the nine checklist rows with evidence (file estimate via Glob/Grep, new module, contracts, dependencies, migrations, more-than-one-mergeable-unit, fog, developers, waits); apply the verdict rules of `FORMATS.md §3`; propose with a one-line rationale per alternative. `bug` type adds: identify candidate red-loop commands (failing test, curl, CLI, browser) — the plan must open with one — and, after the verdict is printed, `ci.failedRun` for the report's branch or commit and `logs.trace` for the error it describes, each returning one more candidate and each `Skip: <role> unavailable` when its adapter is `null`. Completion: verdict and checklist written to `brief.md`, confirmed by the user. Anti-pattern: exploring instead of deciding.

#### `references/reproduce.md`
Procedure: state the symptom as an observable (what is seen, where, what was expected instead), asking when the description carries fewer than three parts; pick the cheapest harness of the five-row table that can carry it — an existing test, a new test beside its neighbours, a command against a running service, the project's CLI, a browser recipe — and go no further down than the symptom requires; **three attempts, each one command**, each recorded in `brief.md` as `- attempt <k>: <what was run> → <what it printed>` and **never in the ledger**, because the `red-check attempt` form derives `phase: execute` and would report an unplanned task as being built. A test written to the current wrong value is green and proves nothing. Reading the implementation for a cause is out of scope — that is the phase after this one. Exit A: the `## Reproduction` block (`Command:`, `Red:`, `Harness:`), copied into `plan.md` as T1 verbatim. Exit B: `Ruling: not reproducible here — <what was tried> — <what would make it reproducible>`, the three attempts and the two ways forward said to the developer (get what is missing, or re-route to `question` or `spike`), and no plan written. Completion: `brief.md` carries a runnable `## Reproduction`, or the ledger carries the `Ruling:` and the developer has the choice in front of them; every attempt is in `brief.md` either way, with what it printed. Anti-pattern: fixing it; explaining it; a test written to the current behavior so that something is green; a fourth attempt because the third nearly worked. Bound: three attempts — the fourth is exit B.

#### `references/research.md`
Procedure: turn open facts into numbered questions; one Explore subagent per question (read-only), answer ≤1.5k tokens with `path:line` facts and a files-to-read list; precedents (≥2 places); external APIs with the installed version from the lockfile and the doc source for that version (`docs.getDocs` pinned; WebFetch/WebSearch is reconnaissance only); risks; a negative result requires a second search of a different shape. Write `research.md`; run `verify-citations.mjs`; failing citations are fixed before use. Completion: every question answered with citations or marked open for grilling. Anti-pattern: a subagent that answers the design question instead of the fact question.

#### `references/plan.md`
Procedure: grilling rounds (frontier → numbered questions → recommended answers → wait → recompute); decisions table; blast radius per task from `codeIndex.blastRadius` on the symbols the task changes — `must_touch` into the task's `Files:`, `may_touch` there or into `## Non-goals` with the reason — `Skip: codeIndex unavailable` when `null` (decision **0091**); tasks as tracer bullets with files, acceptance before code, and the test strategy of `DESIGN.md §6.2` — test-first by default, written as no line at all, or one of the four exemptions with both halves (decision 0022); verify plan mapped to `config.verify.recipes`; refactor-in-scope list; non-goals; for `bug`, T1 is the red loop — supplied verbatim by `references/reproduce.md`'s exit A when the description named no failing command; for `upgrade`, T1 is the project's own commands **run and recorded** on the current version, so that what the bump breaks is separable from what was already broken; for `refactor`, the done-metric is a command with a number. A `spike` plan carries `## Question` (falsifiable), `## Timebox` (what happens at the bell) and `## Exit` (both outcomes, chosen now) **in place of `## Tasks`** and of acceptance criteria, with the ten design fields present as `none — <reason>` where they do not apply (decision **0084**). Prototype rule: one design question, labeled, deleted. Advisory: >250 lines → "check whether this is one mergeable unit". Completion: `Open questions` empty; user approved. Anti-pattern: a plan with "TBD"; a task whose acceptance criterion is "works"; an exemption reason invented outside the four.

#### `references/design.md`
The design-field table (`DESIGN.md §6.2`) with one line of guidance per field, the precedent-first rule, the wrapper rule, and the "design it twice" requirement: 2–3 real alternatives compared in the decisions table by one planner. External APIs: version from lockfile, source per version. One `design.getFrame` here, on plan, and none during execute — the frame's spacing, colors, variants and states become numbers in `### Interfaces` and `### Data & scale`, so execute pulls nothing — and `db.schema` for the tables the task touches, whose columns, nullability and indexes `### Data & scale` carries; each `Skip: <role> unavailable` when `null`, the schema falling back to the migration files it names. Target ≤120 lines.

### 1.2 `run` — S2 kernel

**Purpose.** Own session 2: execute the approved plan task by task, simplify, review loop, verify loop, finish. Resume from the ledger after any interruption.
**Invocation.** `/hodos:run <slug>`.
**Inputs.** `plan.md`, `ledger.md`, `state.json`, rules, code, config.
**Outputs.** Commits; `review.md`/`verify.md` (transient); `plan.md#Outcome`; the finish report.

**Procedure (standing).**
1. `config.mjs find`; read `state.json`; phase `done` → say the task is finished and stop; phase before `approved` → say which S1 step is missing and stop; otherwise `ledger.mjs claim <slug>`, which writes this session's pointer and `active` (decision 0047). A kernel never writes machine state itself (`DESIGN.md §5.1`), and a session that stops claims nothing.
2. Resume by `state.phase` (`FORMATS.md §7`): `approved`/`execute` → `references/execute.md` from `tasks.current`; `review` → `references/review-loop.md`; `fix` → fix per the open findings; `verify` → `references/verify-loop.md`; `finish` → `references/finish.md`; `manual` → tell the user the task is in manual mode and stop.
3. Phases run in order: `execute.md` (+ `defaults.md`) → `review-loop.md` → `verify-loop.md` → `finish.md`.
4. Every fork the plan did not settle: if it changes behavior, contract, structure, or dependency → `AskUserQuestion` with options and a recommendation, then `ledger.mjs add "Gap: …"`; otherwise decide and `ledger.mjs add "Ruling: …"`. Under `config.autonomy == "rulings"` the first case becomes a ruling too, except destructive/outward actions.

**Invariants (first 40 lines).** The plan is the contract; deviations go through the chat. Machine state only via `ledger.mjs`. A diff is judged by the reviewer and the verifier, and walked once by its author in the simplify pass; the kernel never reads one to review it. Subagents are dispatched with the `hodos-*` definitions, never as forks. Commit per task, no push, no merge. Loop bounds are 3 / 2 / 2.
**Completion.** `Finish: report delivered` in the ledger; report in chat.
**Anti-pattern.** Continuing after a red check "with a small workaround"; reviewing the diff inline "to save a dispatch"; declaring done without the verify table.
**Depends on.** `ledger.mjs`, `review-package.mjs`, `hodos-reviewer`, `hodos-verifier`, `campaigns.mjs`.

#### `references/execute.md`
Per task: `ledger.mjs add "Task n: started"` → write the acceptance check first and run it — it must be red — then `ledger.mjs add "Task n: test red"`; a task carrying one of the four exemptions (`visual`/`glue`/`infra`/`no-harness`) skips this and passes `--tests <reason>` on `done` instead (decision 0022) → implement → run the task's check (plus `config.commands.typecheck` when types changed) → red → `ledger.mjs add "Task n: red-check attempt k/3 — …"`; third failure → stop and diagnose in chat → green → mutation check on new tests (break the pinned line, red, restore) → commit with the project convention → `ledger.mjs add "Task n: done" --sha <sha>`. After the last task: simplify pass over `git diff <base>..HEAD`, walking `defaults.md`'s ladder and stopping at the first rung that holds; one emitted line per cut and a closing `net: -<N> lines`; a cut declined because the simpler form is correct but bounded gets a `hodos:` marker in the code instead; commit, `ledger.mjs add "Simplify: done" --sha <sha> --net <n>`. Two shapes are not this loop. **`mechanical`** (the shape of `refactor`): the codemod is the artifact, the red phase applies to the codemod rather than to each file, and the review is packaged `--mechanical <codemod>` — the codemod plus a three-file sample, every other file named under `## Not packaged`. **`spike`** (the type): no red phase, no per-task commit, and no review or verify — work against the timebox, take the exit the plan named, and write one `Ruling:` naming the answer **and the exit**. Completion: every task `done` and `Simplify: done`, `state.phase` reading `review`; a spike satisfies none of the three and completes on §6b's terms instead — the exit taken and the `Ruling:` written. Anti-pattern: two tasks in one commit; a "temporary" `any`; `--tests` on a task the plan did not exempt; a spike that starts committing tasks.

#### `references/defaults.md`
The defaults list (`DESIGN.md §7.2`) as positive one-liners, ordered by the seven-rung ladder the pass stops at the first holding rung of, plus a four-row red-flags table for rationalization ("this case is simple" → "simple cases are where unexamined assumptions cost most"; "the rule doesn't fit here" → "a rule that doesn't fit is a `Gap:` for the chat, not a silent exception"; "I'll clean it up later" → "later is the simplify pass, and it runs now"; "the test is basically right" → "prove it with mutation"). Carries the two forms the pass writes: a cut line `L<line>: <tag> <what>. <replacement>.` over `delete/stdlib/native/yagni/shrink`, closing with `net: -<N> lines`; and the marker `hodos: <ceiling> — upgrade when <trigger>` for a cut declined because the simpler form is correct but bounded — both halves mandatory, never for unfinished work and never for a known defect (decisions 0017, 0018). Target ≤100 lines.

#### `references/review-loop.md`
`review-package.mjs <slug>` → dispatch `hodos-reviewer` (`model: config.models.review`) with the input path, the rules dir, the config path → wait for the completion notification → read `review.md` (verdict + findings only) → `ledger.mjs add "Review k: <verdict> b/m/mi"` → `ACCEPT` → done; otherwise fix blockers and majors (minors if cheap), commit, `ledger.mjs add "Fix k: done" --sha <sha>` → iteration 2: `review-package.mjs <slug> --since <fix-sha>`, dispatch again with the previous `review.md` → still not `ACCEPT` → `AskUserQuestion` breaker: accept with open findings / continue manually / roll back to task N → `ledger.mjs add "Breaker: review — <choice>"`. Never tell the reviewer what not to flag. Completion: `ACCEPT`, or a `Breaker:` line. Anti-pattern: a third iteration; pre-judging findings in the dispatch prompt.

#### `references/verify-loop.md`
`env.mjs up` before the dispatch and `env.mjs down` on every path out (decision 0074): a blocked layer is one `AskUserQuestion` offering to write the `permissions.allow` entries, whose decline degrades that layer's `browser` and `http` claims to a skip with the reason and leaves the command recipes running; a layer still red at its own timeout is one `hodos-preparer` dispatch, then `env.mjs probe` here, then §9's breaker if it is still red. No profile declared, and `commands.dev` is the environment, unchanged. Then dispatch `hodos-verifier` (`model: config.models.verify`) with the plan path, the recipe names whose `when` matches, the adapter path, the evidence path → wait → read `verify.md` verdict → `ledger.mjs add "Verify k: <PASS|FAIL> n claims, s skipped"` → `FAIL` → fix, commit, `ledger.mjs add "Fix k: done" --sha <sha>`, re-dispatch (iteration 2 re-verifies the failed claims) → still `FAIL` → breaker. Verify fixes are not re-reviewed; they are listed in the finish report. Completion: `PASS`, or a `Breaker:` line.

#### `references/finish.md`
Fold `review.md` + `verify.md` into `plan.md#Outcome` (verdicts, open minors, evidence paths, gaps count); delete the transient files; campaign node → `campaigns.mjs node-done <campaign> <node> --sha <sha>` and `campaigns.mjs measure <campaign>`; proposals only where a finding traces to a missing convention, with two `Grep` counts behind them — ≥2 precedents of the target → a rule proposal, 0–1 precedents with ≥2 of the flagged shape → a convention proposal the developer decides rather than confirms, neither → an observation line (decision 0050); an accepted proposal of either kind is written by invoking the `rule` skill (decision 0016), never by hand; hook proposal on a repeated rule violation; `tracker.link` once on the id the branch name or the brief's ticket key carries, which is outward-facing and therefore a mandatory stop under every autonomy setting (`DESIGN.md §4.4`) — declined, `null`, or no id → `Skip: tracker unavailable`, and the report carries a `Tracker:` line either way; `ledger.mjs add "Finish: report delivered"` (the script appends the history line and removes every pointer naming the task, `active` included); report to chat: done / gaps / rulings / open minors / proposals / "delete `tasks/<slug>`?" → on yes, delete the directory. At most **one** offer line, on the same script-decidable preconditions and the same priority as the digest's (`FORMATS.md §12`), silent by default — a silent run produces nothing and the report does not mention it. A `spike` arrives here from `approved` with no review and no verify to have passed: `## Outcome` and the `Ruling:` both name which exit was taken, the branch is the developer's to delete, and nothing merges. Completion: report delivered, node updated. Anti-pattern: a rule proposal from a single incident; "Great, all done!" before the table.

### 1.3 `init`

**Purpose.** Learn the project once; write the project layer with approval.
**Invocation.** `/hodos:init` · `/hodos:init --refresh`.
**Inputs.** The repository; existing AI instructions; `.mcp.json`; the developer.
**Outputs.** `CLAUDE.md` map or managed block; `.claude/rules/*.md`; `.claude/hodos/config.json`; `.gitignore` entries; `permissions.allow` for hodos scripts in `.claude/settings.local.json` (on approval); approved hooks in `.claude/settings.json`; the migration ledger applied.

**Procedure.** Steps 0–8 of `DESIGN.md §8`, each in its reference:
- `references/scan.md` — inventory checklist; area briefs for Explore subagents (`model: config.models.initScan` or `sonnet` before a config exists): stack & commands from scripts/Makefile/csproj/CI; architecture from folder layout, import direction, DI; conventions from 5–10 representative files per area hunting Unusual/Opinionated/Tribal/Consistent with ≥2 precedents; tests: framework, structure, mocking, what is asserted; existing-instructions inventory; nested project detection; commit-convention detection from `git log`.
- `references/interview.md` — recall questions in batches ≤8; the standing questions (what Claude gets wrong here; why this pattern, not the default; exceptions; how to run for verify — ports, auth, test data; what not to touch; tracker/branch/commit; language); never ask what the scan answered; when the repo contradicts the developer, show the evidence and ask.
- `references/rules.md` — the three sources, the three-question filter, the rule form (`AUTHORING.md §10`), sources fetching (`sources/<stack>.md` → `docs.getDocs`/WebFetch → candidates), the report-before-write table (rule, paths, precedent, source, justification, the `keep`/`target` judgement and what carries it, form).
- `references/config.md` — the field list the write step reads instead of the specification (decision **0066**): the four fields `init` computes and where each value comes from, then every key with what it admits, ≤60 lines, derived from `FORMATS.md §2` and citing it.
- `references/migrate.md` — the ledger for existing instructions: one entry per instruction, `retain / rewrite / relocate / automate / delete`, evidence, what is lost, approval flag; a relocation target must itself be loaded or behind an observable trigger; nothing lives in two loaded files.
Write phase: managed block `<!-- hodos:begin -->…<!-- hodos:end -->` in an existing `CLAUDE.md`, a new ≤60-line map otherwise; rules with `paths:` and anchored precedents; config from `references/config.md` with commands **run once** and `verifiedAt`/`scanSha` recorded; `.gitignore`; `permissions.allow: ["Bash(node <plugin root>/scripts/*)"]` in `.claude/settings.local.json`, the plugin root resolved from `${CLAUDE_PLUGIN_ROOT}` in the skill body rather than written literally (decision 0057); hooks only if approved, and into the committed `.claude/settings.json`. Self-check: `config.mjs check`, then `lint.mjs --project`.
`--refresh`: `git log --diff-filter=DR --name-only <scanSha>..HEAD`; precedents that have rotted — a citation that no longer resolves, an anchor whose text has moved, a bare path that is gone (decision **0078**), the last two through `lint.mjs --project`; drift counts; new areas; a delta report before write.
**Completion.** Config verified by running its commands; lint green; every write approved.
**Anti-pattern.** Rules that restate what the model knows; asking the developer to confirm a path-checked fact; rewriting an existing `CLAUDE.md`.
**Limits.** Kernel ≤150; ≤8 questions per batch.

### 1.4 `campaign`

**Purpose.** Create or advance a campaign map.
**Invocation.** `/hodos:campaign <idea>` · `/hodos:campaign <slug>` (advance). On a campaign verdict, `task` invokes this skill through the Skill tool (decision 0016).
**Procedure** (`references/map.md`): campaign-level grilling (goal; done-metrics as commands with expected numbers, measured now via `campaigns.mjs measure`; architecture direction D1..Dn; decomposition — tracer bullets or expand–contract; fog list; waits); write the map (`FORMATS.md §11`); `campaigns.mjs frontier <slug>`; propose one node; on confirmation invoke the `task` skill as `<slug>/<node>` and `campaigns.mjs claim <slug> <node> <owner> <branch>`. Advance mode: re-measure, show frontier/blocked/fog/waits; empty frontier → name the wait and propose nudge / pull from fog / drop. Decision and research nodes resolve in-session and append a `D` row. Changing a campaign decision happens here, never inside a node.
**Completion.** Map written; one node proposed or started; metrics current.
**Anti-pattern.** Cutting fog into nodes; a map that retells a task's plan; resolving two nodes in one session.
**Depends on.** `campaigns.mjs`, `task`.

### 1.5 `status`

**Purpose.** Show state and hygiene.
**Procedure.** `state-digest.mjs --full`; `config.mjs check`; `lint.mjs --project`; `ledger.mjs sessions` (`--gc` on confirmation); `campaigns.mjs find` + `frontier` for each map, which from Stage 9a `state-digest.mjs --full` carries in-process — one Node start on that budget, not two. Shows: active tasks with phase and last event; stale tasks (`ledger.md` mtime older than `staleDays`) with "fold or delete" prompts; campaigns: frontier, blocked, fog, waits, claims seen on branches; upgrade rate from `history.jsonl` (tasks with `upgrades > 0` / tasks finished in the last 30 days), the override rate (`overrode`) and the last five `gapTexts` beside it (decision 0046) — under three finished tasks in the window the counts print and the percentages are withheld with the reason (decision 0051); `--cost` as its own run, printing each task's token counts from `usage` and their totals, and no dollar figure (decision 0045); lint results (rules whose `file:line` precedents no longer resolve or whose anchors have moved, bare paths that are gone, over-cap files, frontmatter warnings). Offers actions; performs deletions only on confirmation.
`--debt` is a separate read-only run: grep the project for `hodos:` markers (skipping `node_modules`, `.git`, build output), one row per marker grouped by file — `<file>:<line>, <what was simplified>. ceiling: <the limit>. upgrade: <the trigger>.` — tagging any marker that names no trigger `no-trigger`, closing with `<N> markers, <M> with no trigger.` or `No hodos: debt.` It changes nothing (decision 0017).
`--prune` is a third run of its own, over `references/prune.md`: `lint.mjs --rules` prints the four facts decision **0082** names — each rule's age (first arrival, followed through renames, or `age unknown — not committed`), its size in lines, its precedents and which of them have rotted — a citation that no longer resolves, or an anchor whose text has moved (decision **0078**) — plus the layer's token cost — and one `AskUserQuestion` per rotted rule offers keep · re-point · delete. It calls no rule dead — nothing measures that (decision **0082**) — and it is the only place this skill deletes a file the developer wrote.
**Completion.** Digest printed; every stale item has a proposed action; `--debt` prints the ledger and its count; `--prune` asks only about rules whose citations have rotted.

### 1.6 `rule`, `skill` and `adapter`

`rule` is model-invocable: the finish phase invokes it for an accepted rule proposal (decision 0016). It writes one project rule by `AUTHORING.md §10` — grep for precedents first, run the three-question test aloud with evidence, draft, confirm, write to `.claude/rules/<name>.md` with `paths:`, `lint.mjs --project`. Refuses to write a rule that fails question 2.
`skill`: write one project-specific skill (a procedure the project needs and hodos does not ship — e.g. "regenerate the API client") by `AUTHORING.md §11`; register it in the CLAUDE.md map.
`adapter`: write one project adapter into `.claude/hodos/adapters/<role>/<tool>.md` and set its config entry to `project:<tool>` (decision 0062). Three questions, the first of which refuses: is the server in `.mcp.json` or merely live in this session · does one of the eight roles call it · what does the schema not say. Every tool id comes from a live schema. All three are small skills (`AUTHORING.md §7`).

### 1.6a `review` and `handoff`

Both are small skills, both `disable-model-invocation: true`, added by decision **0081** where the entry is not a task at all. The model-invocable set stays at three.

`review`: `/hodos:review [branch|ref|a..b|path]`, defaulting to the current branch. `review-package.mjs --target <t>` writes the package to a temporary directory; one `hodos-reviewer` is dispatched against it with `config.models.review`; the verdict, the blockers and majors, the reviewer's Coverage line and the path to `review.md` are printed. Nothing is created in the project — no task, no ledger line, no branch — and a target whose branch an unfinished hodos task is on is refused by name, because `/hodos:run <slug>` reviews that diff against its plan. Completion: a verdict printed and `git status` unchanged.

`handoff`: `/hodos:handoff [slug]` writes `.claude/hodos/handoffs/<slug>.md` (`FORMATS.md §16`) from `plan.md`, `state.json` and `ledger.md` — header, `Reviewed:`, where it stands, the open ledger lines, the plan verbatim, the next step. Tracked, uncommitted; the developer commits it, and `/hodos:run <slug>` on another machine offers the pickup and deletes the file (decision **0083**). It writes no ledger line and does not touch the task directory. Completion: the file exists, `git status` shows it as the one new file, and the developer knows what to commit and push.

### 1.7 `wait-what`

In the developer's voice: "Wait, I lost you. Re-pitch where you are: a sentence of context, plain technical English, the project's own terms, what you need from me." User-invoked; ≤10 lines.

## 2. Agents

**Dispatch semantics (all agents).** The kernel dispatches with the Agent tool naming the definition as `subagent_type: "hodos:<agent>"` — the plugin-qualified form, verified 2026-09-01 (`PLATFORM-NOTES.md` fact 33); the bare name is rejected with the list of available agents, and is an error rather than a fallback. `model` is passed per dispatch from `config.models.<role>`, which the Agent tool honours (fact 34). The per-dispatch turn bound is **not** passed: `maxTurns` is a field of the definition itself (facts 36 and 40, decision 0044) — a machine bound on an agent, where the 3 / 2 / 2 of `DESIGN.md §4.5` bound only the kernel. An agent that reaches its bound returns **nothing** — no verdict line and no output file — so the kernel stops with that diagnosis instead of recording a verdict, and never resumes it. Dispatch runs in the background: the kernel does not poll or sleep — it waits for the completion notification, then reads the agent's output *file* (`review.md`, `verify.md`), never its transcript. The dispatch message contains paths and one-line instructions only — no pasted plan, no pasted diff, no conversation history. Agents write exactly one output file (plus `evidence/` for the verifier) and return exactly one verdict line. Agents do not dispatch agents.

### 2.1 `hodos-reviewer`

`model: opus` (overridden per dispatch by `config.models.review`) · `tools: Read, Grep, Glob, Bash, Write` · the prompt restricts `Write` to `review.md` and forbids any change to the tree, index, HEAD, or branches.
**Inputs.** Path to `review-input.md`; the rules directory; `config.json` (for commands); for iteration 2 the previous `review.md`.
**Procedure.** Run `config.commands.test`, `typecheck`, `lint` verbatim (`null` → `check: not configured`); record results — once per project the package's `## Projects` names, wherever it carries that section, each in its own directory and each of those rows suffixed ` · project: <dir>` (decision 0076). Read the input file. Spec section: Missing / Extra / Misunderstood against the plan's goal and tasks; a task's `Tests:` exemption whose stated reason does not hold on the diff — a branch under `glue`, logic under `visual` — is a `major` (decision 0022). Standards section, two passes. Convention pass: findings against project rules, the plan's design fields (dependency direction, data assumptions, refactor-in-scope both ways), the defaults list. Behavioral pass: the nine-row risk checklist carried in the prompt (`L1` shadow override · `L2` type-contract breach · `L3` boundary blindspot · `L4` state-mutation hazard · `L5` control-flow escape · `L6` callee-contract mismatch · `L7` concurrency/async · `L8` resource lifecycle · `L9` time/locale) run over the diff — the axis `defaults.md` does not cover, because it names what a model writes by default, not what it fails to see (decision 0015). Each finding = severity + `file:line` + item + one-line fix; a behavioral finding at `blocker` or `major` also carries a trigger, the concrete input or state under which it manifests. Confidence pass: drop any finding you cannot ground in a specific line and item, and any behavioral finding at those severities whose trigger you cannot name. Coverage: name what you did not review. Write `review.md`; return only the verdict line.
**Standing facts in the prompt.** The code was written by another agent. The implementer's report is testimony; a rationale never lowers severity. Inspect outside the diff only for one named risk with one focused check; unverifiable → a "cannot verify from diff" item for the orchestrator. Do not dispatch subagents. Skip anything the tooling already enforces. Praise is one line, at the top, only where earned.
**Completion.** `review.md` valid per `FORMATS.md §9`; verdict returned.
**Anti-pattern.** Findings without a location; "would look cleaner"; re-ranking Spec against Standards; crawling the codebase.
**Limits.** Prompt ≤150 lines; ≤400 words per section.

### 2.2 `hodos-verifier`

`model: sonnet` (overridden by `config.models.verify`) · no `tools` allowlist (inherits the session's tools including the browser adapter's MCP tools) · `disallowedTools: Edit, NotebookEdit` · the prompt restricts `Write` to `verify.md` and `evidence/`. A background subagent keeps every MCP tool (`PLATFORM-NOTES.md` fact 13, confirmed live by fact 41: a dispatched verifier answered with all 29 `mcp__chrome-devtools__*` names), so the verifier drives the browser from the background and there is no foreground path.
**Inputs.** Plan path (acceptance criteria + verify plan); recipe names; adapter file path; `evidence/` path; the profile the kernel raised, where the project declares one, which the verifier writes into `verify.md`'s first line (`FORMATS.md §10`, decision 0074). One config path and one recipe-name list per project the diff touches — the projects `review-input.md`'s `## Projects` already names, computed by `config.mjs for-files` over the diff and not predicted from the plan's `Files:` lines (decision 0076); where it names any, each row that reports a command that ran or an action that was taken carries ` · project: <dir>` in its command cell, and a row copied forward from an earlier iteration keeps the one it had (`FORMATS.md §10`).
**Procedure.** For every claim in the plan's tasks and verify plan: choose the recipe; run the command or drive the browser via the adapter (navigate → snapshot → act → screenshot to `evidence/<nn>-<name>.png`, console and network checked for errors; an `a11y` recipe audits the route and reports by `impact`, a `viewport` recipe re-visits it at each declared width — decision 0095); record claim → command → evidence → status. Sample ≥1 new test for mutation (break the pinned line, run, red, restore). `perf` recipes only if the plan declared them. Every skip has a reason; a claim missing from the table is a failure. Write `verify.md`; return the verdict line.
**Standing facts.** No claim without a command run in this message. Browser is for CSS/layout/cascade/animation/hover/breakpoints; a logic bug found in the browser becomes a finding "+ cover with a test". Never mock away the thing under test to make it pass.
**Completion.** Table complete and its header counts equal the rows; verdict returned.
**Anti-pattern.** "Tests pass" without output; screenshots without a claim; a route dropped from the table.

### 2.3 `hodos-plan-reviewer`

`model: opus` (overridden by `config.models.planReview`) · `tools: Read, Grep, Glob, Write` (writes `tasks/<slug>/plan-review.md` only) · `deep` path only.
Reads the plan, the research, the rules. Reports gaps that would cause real problems in implementation: missing design fields, ambiguous acceptance criteria, contradictions with rules or precedents, unstated assumptions about data/scale, decisions without a real alternative, and a `spike` plan's numeric bar with no statistic to read it on (decision **0088**). Approve unless there are serious gaps. Output ≤300 words; no rewriting of the plan. The kernel deletes `plan-review.md` after folding.

### 2.4 `hodos-preparer`

`model: sonnet` (overridden by `config.models.preparer`) · `maxTurns: 25` · `tools: Read, Grep, Glob, Bash, Write` (writes `tasks/<slug>/env.md` only) · dispatched by the **run kernel** before the verifier and never by it, because an agent that raises the environment and then grades what runs in it has an interest in the result (decision 0074).
**Inputs.** The layer's name, the directory its commands run in and the check that is still red; the config path; the layer's log under `.claude/hodos/env/`; the output path.
**Procedure.** Read the log and the failing check; re-run that check by hand — green now means the layer's `timeout` is too low for this machine, which is itself the finding; name one cause; fix and re-raise where the cause is the environment's; write `env.md` per `FORMATS.md §17`; return `raised` or `still red` with the cause in one clause.
**Standing facts.** One layer, the one the dispatch names. The project's source, tests and config are not what is broken. A cause it cannot fix from here — a credential, a machine grant, a service someone else owns — is a complete answer with what would close it. Do not dispatch subagents. Do not run the task's claims.
**Completion.** `env.md` written and the verdict line returned; the kernel re-probes the layer itself.
**Anti-pattern.** Editing the project to make a check pass; raising a layer it was not given; "should work now" with no re-run behind it.
**Limits.** Prompt ≤150 lines; one dispatch per entry into `verify-loop.md §3`.

## 7. Bench — `bench/`

The directory is named `bench/`, not `evals/`, to stay clear of the platform's own `claude plugin eval` layout (`PLATFORM-NOTES.md` check K).

Every bench metric is labeled **gate** or **measurement**. A gate carries a threshold and a failing run fails the stage; a measurement is recorded and read, never thresholded. The split exists so a number that looks good cannot stand in for a behavior that broke — the canonical case is a shorter diff that no longer runs (decision 0019). `router/`, `review/` and `noop/` scores are gates; sizes, token counts and costs are measurements.

- `fixtures/webapp/` — React + TS + Vite front end (3 routes, TanStack Query, a zustand store, vitest, eslint); `fixtures/api/` — Node HTTP API with tests; `fixtures/mono/` — a root `package.json` with two workspaces `web/` and `svc/` (monorepo fixture for nested configs and root-map lookup); `fixtures/kit/` — a tiny component library used as the "second repository" for external campaign maps. Each has 3–4 deliberate conventions (`http` client wrapper, error shape, module layout) documented in `fixtures/README.md` with `file:line`; committed with `package.json` + lockfile, `node_modules` ignored, CI runs `npm ci` in each. Fixtures ship **without** `.claude/`; Stage 3 produces one for `webapp` and commits it so later stages have a config.
- `scripts/fixture-copy.mjs <name> [--strip-claude]` — copies a fixture to a temp directory, runs `git init`, seeds three conventional commits so `git log`, `scanSha`, and commit-convention detection have a source, and prints the path. Every stage test that runs hodos against a fixture uses this copy, never the checked-in tree.
- `router/set.json` — 35 task descriptions, each labeled with the expected path (`quick` · `standard` · `deep` · `campaign`), type, and campaign flag, and carrying the nine checklist rows of `FORMATS.md §3` that produce that path, so a label is derived rather than chosen (decision 0025); `router/run.mjs` scores accuracy and re-derives every label from its rows; `router/invoke.mjs` drives the scored run — a fixture copy per case, the invocation arm, the printed verdict and the tool-call count parsed out of it — and writes the verdicts file (decision 0027); `router/README.md` states which invocation path is used (check D). Thresholds: path ≥85%, type ≥90%, campaign flag ≥90% — gated at Stage 11, which owns the bench; Stage 4 records one run as a measurement, because a full run costs a quarter of a day's usage and a gate nobody can re-measure after a fix is not one (decision 0028).
- `run/plans/<name>.md` — approved plans the `run` kernel is exercised against, each shaped for one behavior (a `visual` exemption beside a test-first task, a correct-but-bounded form, a diff with nothing to cut, an acceptance check that cannot pass); `run/seed.mjs <plan> [--fixture <name>] [--gap] [--autonomy ask|rulings] [--at approved|review|verify|finish] [--defect <patch>] [--rule-arm one|two]` turns a `fixture-copy.mjs` copy into a task directory — writes `plan.md`, runs `ledger.mjs init` and `ledger.mjs add "Plan: approved"`, creates the branch — and prints the copy's path; `--at review` continues past that point: it commits each task's implementation from `plans/<name>.impl/` and, with `--defect`, one seeded patch inside the task commit it names, running `ledger.mjs` for every event so the copy arrives at `phase: review` through the same script that would have written it live (decision 0036); a task the plan exempted records the exemption on its `done` line instead of a red run it never had (decision 0022), `--at verify` adds the `Review 1: ACCEPT 0/0/0` a clean implementation earns (decision 0043); and `--at finish` installs `plans/<name>.finish/{review-<arm>,verify}.md` and its `evidence/` into the task directory, then writes the gap, the ruling and the passing verify a run would have left, with the ledger's counts read out of the artifacts rather than written twice — `--rule-arm` picks which review is installed, one naming a pattern the code carries twice and one a pattern it carries once, which is the pair the ≥2-occurrences rule of `DESIGN.md §7.5` is tested against (decision 0048); `run/README.md` names each plan and the criterion it serves. A **harness, not a bench**: it produces inputs and scores nothing, so it carries neither gate nor measurement (decision 0033). Stages 6, 7 and 8 seed their own inputs with it.
- `review/seeded/<id>.patch` — ≥18 patches applying one seeded defect each to a fixture copy, each carrying its own metadata (fixture, kind, item, line, and the trigger for a behavioral one), ≥12 of them convention defects tagged by defaults-list entry or fixture rule and ≥6 behavioral across distinct `L` codes (decision 0015), plus `review/clean.json` listing 6 files that must produce no finding. The patches are grouped into review packages of three or four so the reviewer sees a task-shaped diff rather than one defect, which is both the realistic input and the affordable one (decision 0037). `review/invoke.mjs` builds the packages, dispatches the reviewer and writes the verdicts file; `review/run.mjs` scores recall per kind and precision from it and makes no model call, the split of decision 0027. Thresholds, gated here: recall ≥80% overall and ≥80% for each kind, precision ≥85%.
- `report.mjs` — where a metric is labeled `gate` or `measurement`, for all three scorers' `--json`. It refuses the two ways a label drifts: a gate built without a threshold, and a measurement built with one (decision 0019).
- `noop/scenarios.json` — each scenario: the rule under test as `lines`, **every** file and line that states it, a fixture task prompt, and the behavior the rule is supposed to change, stated as a checkable direction. A rule has more than one home because the plugin ships its own specification beside the skills that restate it, and a control that removes one line removes no rule (decision 0073); a home embedded in a line carrying other rules names a `replaceWith`, the same line with the rule's clause taken out. `--check-scenarios` holds each named line to appearing in its file **exactly once** — a line written twice would take two behaviors with it — refuses a `replaceWith` equal to its line, and holds each check to one of six kinds (`transcript`, `transcript-absent`, `file`, `rows`, `metric`, `path-absent`), which is what keeps a scenario checkable from what the run left behind rather than from a reading. `noop/run.mjs` runs the prompt in two arms, with the line and with it removed, and a scenario passes only when the arms differ in the declared direction: the without-line arm is the control and is *expected to fail* the check — that delta is the whole signal, and without it "the behavior differed" is the reader's judgement rather than a result. Gate, with its threshold set from the first run that can produce one. Stage 11a bought two and neither could: run 1's control kept the rule, and run 2's — which removes every prose home of it — read 0 of 6 because the checked behavior happens in both arms, the arms differing only in turns, which decision 0019 forbids gating (decision 0073). The threshold stays unset rather than invented, and `--check-scenarios` carries a `probe` per scenario that reads the control copy for a surviving statement of the rule, so an unmeasurable scenario is found before a session is bought. The scorer is covered by `node:test` unit tests that make no model call, separately from the scored run that does (decision 0019). The output is also the evidence for the PR policy in `AUTHORING.md §13`.
- `docs/BENCH.md` documents how to run each and restates the thresholds above.
