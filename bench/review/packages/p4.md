# Plan — order-list-filters
Path: standard · Type: feature · Tasks: 3

## Goal
The list endpoint takes a minimum total and returns one page at a time: `GET /orders?status=paid&min=10`.

## Non-goals
Sorting. A cursor. Any change to how an order is stored.

## Design
### Modules
`src/services/orders.js` — the filter and the paging helper. `src/routes.js` — the query parameters the route passes through.
### Dependency direction
`routes → services → store`, one way, as the lint config already enforces. A liveness endpoint, if one is ever added, is a row in the route table like every other route.
### Interfaces
`list(status: string | null, min?: string): Order[]` · `page(orders: Order[], offset: number, limit: number): Order[]`
### Invariants & failure modes
Every failure this service reports is an `AppError` with the code the client reads. A page of `limit` rows holds `limit` rows where the collection has them.
### Data & scale
Three seeded orders in memory; the collection is small enough to filter in full before paging.
### Precedent
`src/services/orders.js:14` for the status validation this filter follows; `src/errors.js:5` for the error type.
### Refactor in scope
`list`'s signature, for the new parameter. The service's own tests may gain the case for the literal `all` it already handles.
### External APIs
None.
### Architecture alternatives
Filtering in the store was declined: the store holds orders and nothing else, and a query language there is a second place to look for behaviour.

## Tasks
### T1. The minimum-total filter
Files: `src/services/orders.js`, `src/routes.js`. Acceptance: `min` narrows the list; a `min` that is not a number is rejected with the code the client reads and a 400.
### T2. The paging helper
Files: `src/services/orders.js`. Acceptance: `page(orders, 0, 2)` returns the first two orders, and `page(orders, 0, 1)` returns the first one.
### T3. Cover the filter
Files: `test/services.test.js`. Acceptance: the literal `all` behaves as no filter.
